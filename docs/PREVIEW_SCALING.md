# 预览缩放与真实观感

> 结论先行：**缩到 100% 以下的预览必须做"浏览器 / 设计软件显示一张导出图时做的那件事"——按屏幕物理像素、
> 用 mipmap 逐级平均 + 双线性缩下去，绝不最近邻抽样。** 抽样出来的 10% 预览又脆又干净，但那是一张根本不存在的图；
> 导出图放进 Figma 缩到 10% 看到的是颗粒融成一片的"糊"，预览必须把这份糊如实给你看，你才能在导出前决定颗粒要多大。

## 1. 现象

画布 1000×600，预览 10%。预览里颗粒清晰、点点分明；把导出的 1000×600 PNG 放进 Figma / 浏览器，
以 10% 的尺寸显示，颗粒"糊到一起"，跟预览完全两样。

## 2. 原因

以前预览画布的后备存储永远是画布全尺寸（`canvas.width = 1000`），缩小全靠 CSS 把它显示成 100px 宽，
而 `.slot__canvas { image-rendering: pixelated }` 让 Chromium 用**最近邻**做这次降采样：每 10 个像素只挑 1 个。

抖动图是接近奈奎斯特频率的周期信号，对它抽样得到的是**拍频**——一个更粗、更规则的假颗粒图案，
所以预览里的"点"比真实颗粒大、排得整整齐齐。（高分屏 DPR=2 时是每 5 个挑 1 个，同一回事。）

Figma、浏览器 `<img>`、macOS 预览显示一张图时做的是 mipmap / 面积平均：每个屏幕像素是它盖住的所有源像素的平均。
1 位的黑白颗粒平均之后就是灰，这才是导出图缩小后真实的样子。

预览不是"错在渲染"，而是错在**用了一种没有任何消费方会用的缩放方式**。

## 3. 现在的做法

`displayGeometry(width, height, scale, dpr)`（`frontend/src/engine/preview.ts`）按画布尺寸、缩放档位和
devicePixelRatio 算出预览画布的显示几何，`SlotCanvas` 照它摆：

| 模式 | 条件 | 后备存储 | 帧怎么落上去 | `image-rendering` |
|---|---|---|---|---|
| `nearest` | 屏幕物理像素 ≥ 画布像素（100%、高分屏上的 50%） | 画布尺寸 | 原样贴帧 | `pixelated`，放大交给 CSS 最近邻，每个像素都是实的 |
| `area` | 屏幕物理像素 < 画布像素（10%、25%、适应窗口……） | 屏幕物理像素（CSS 尺寸 × DPR） | `resampleForDisplay`：mipmap 逐级 2×2 平均 + 双线性 | `auto`，后备存储与屏幕一比一，浏览器不再抽样 |

1000×600 画布常见组合：

| 缩放 | DPR | CSS 尺寸 | 后备存储 | 模式 |
|---|---|---|---|---|
| 100% | 1 | 1000×600 | 1000×600 | nearest |
| 100% | 2 | 1000×600 | 1000×600 | nearest（CSS 放大 2×） |
| 50% | 2 | 500×300 | 1000×600 | nearest（物理像素正好一比一） |
| 25% | 2 | 250×150 | 500×300 | area |
| 10% | 1 | 100×60 | 100×60 | area |
| 10% | 2 | 100×60 | 200×120 | area |

细节：

- `resampleForDisplay`（`engine/preview.ts`）照着 Chrome 显示 `<img>`、GPU 贴纹理的路子走：先用 `box` 核按 2×2 平均
  逐级缩到「不小于目标」的那一级 mipmap（1000 → 500 → 250 → 125），再用**不展宽**的双线性（`linear` 核，
  GPU 采样一个纹理坐标只看最近的两个纹素）缩到目标尺寸（125 → 100）。核复用引擎里源帧重采样的实现
  （`preprocess/resample.ts`）：预乘 alpha、边缘归一化。在 sRGB 空间取平均，不做线性化——浏览器与 Figma 也是这么做的，
  要的是跟它们一致，不是物理正确。
- 为什么不是一次精确的面积平均：对着 Chrome 里 `<img>` 显示导出 PNG 的截图实测（1000×600 缩到 10%），
  逐像素平均差 mipmap 路线 3.4/255、精确面积平均 11/255、旧的最近邻抽样 71/255；按 4×4 块比"多花"（块内标准差），
  mipmap 路线差 2.2、面积平均差 9.0、最近邻差 71。面积平均比真实显示更平滑，mipmap 路线连残留的纹理都对得上。
- 同一帧、同一目标尺寸只算一次（`areaCache`），滑块连续拖动时每帧算一次，1000×600 缩到适应窗口约 10ms。
- 播放中的降分辨率帧（`rendered.scale < 1`）走同一条路：比屏幕像素多就缩，比屏幕像素少就按最近邻铺开。
- DPR 由 `useDevicePixelRatio` 跟踪，窗口拖到另一块屏或系统改缩放时后备存储跟着重开。
- 「原图」页在 area 模式下直接用浏览器的平滑缩放画源帧（源帧是照片，浏览器缩它跟网页里显示它一样）。
- 界面预览窗口取帧走 `slotCanvasRegistry`，登记的是函数而不是元素：area 模式下屏幕上那块 canvas
  只有物理像素那么大，拿去当帧源会糊，画布按需补一份全尺寸副本（只在真的有人要帧时才画）。
- 读像素的 UI 用例（数颜色、比 SVG 栅格化结果、按亮度统计）先切到 100%：只有那时后备存储才是原样的帧。

## 4. 与各个消费方的差异

| 消费方 | 缩小方式 | 与本预览的差异 |
|---|---|---|
| Chrome `<img>` | 先缩到不小于目标的 2 的幂 mip 级（逐级 2×2 平均），再双线性 | 就是本预览模拟的路线，实测 10%/DPR 1 逐像素差 3.4/255 |
| Figma / Sketch / Keynote 等 GPU 渲染 | 纹理 mipmap + 双线性或三线性 | 同一路线；三线性会再混一级更小的 mip，略更平滑 |
| macOS 预览 / Quick Look / Finder | CoreGraphics 面积平均 | 比本预览更平滑一点，残留纹理更弱 |
| Photoshop | 双三次系 | 略锐一点，可能有轻微振铃 |

这些差异都远小于"抽样 vs 平均"的差异。所有消费方都在 sRGB 空间取平均，本预览亦然。
高分屏（DPR 2）上 10% 是 5× 缩小，mip 级取 4×、再双线性缩 1.25×，残留的细纹理在本预览与 Chrome 里都有，
只是相位不完全一样——按块比灰度与"多花"都对得上（块均值差 ≤ 1/255 的系统差外，块标准差差 4.9/255）。

## 5. 想让缩小之后仍然清楚，该怎么选参数

定义**有效颗粒尺寸**：

```
E = 像素尺寸 P × 预览缩放 z × devicePixelRatio
  = 一个抖动颗粒在屏幕上占几个物理像素
```

**E 是 ≥1 的整数**时每个屏幕像素正好盖住整数个颗粒，颗粒边界与像素边界对齐，
缩小后仍是干净的 1 位图案；E<1 时一个像素盖住不到一个颗粒，颗粒必然融成中间色。

1000×600 画布、10% 预览、DPR=1：

| P | 横向颗粒数 | E | 缩小后的结果 |
|---|---|---|---|
| 4 | 250 | 0.4 | 每像素盖 2.5 个颗粒，中间调全成灰 |
| 5 | 200 | 0.5 | 每像素盖 2 个颗粒，只剩 3 级灰 |
| 8 | 125 | 0.8 | 每像素盖 1.25 个颗粒，灰 + 残留结构 |
| 10 | 100 | 1.0 | 一颗粒 = 一像素，**干净** |
| 20 | 50 | 2.0 | 一颗粒 = 2×2 像素，干净 |

规避：

1. 像素尺寸取 `10 / z / DPR` 的倍数——10% 下 P 取 10、20、30…；高分屏（DPR 2）上 5、10、15… 也成立。
2. 或改画布尺寸：想用 P=8 就把画布设成 800×480，10% → 80×48，每颗粒正好 1px。
3. 最根本：最终素材就是 100×60，就把画布设成 100×60、用 100% 预览工作，像素尺寸 1 / 2 / 3 直接就是"几个最终像素一个颗粒"。

mipmap 路线（Chrome / Figma / 本预览）里 10× 不是 2 的幂，最后一步双线性还会把相邻颗粒混一点；
要完全干净，E 还得是 2 的幂（P=20 在 DPR 1 的 10% 下 E=2）。
